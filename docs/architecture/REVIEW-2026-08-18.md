# Architecture & Documentation Review — 2026-08-18

*Revised after human decision review. See "Revision note" at the end of this document.*

Scope: review of `01-runtime-flow.md`, `02-component-architecture.md`, `03-implementation-dag.md`,
`04-agent-execution-flow.md` against the approved diagrams in `visual/`, plus a review of the
initial architecture itself.

Method: the four `.html` files are bundled pages (gzip+base64 payloads); the inner document was
extracted and reduced to text, then diffed node-by-node against each `.md`. No architecture file was
modified by this review.

**Verdict:** the architecture is fundamentally sound and does not need to be redrawn. Package and
responsibility boundaries are strong. The translations are high quality and safe to hand to
downstream agents. Remaining work is concentrated in four places — contract semantics, concurrency
policy, platform risk, and documentation fidelity — plus some early implementation-risk reduction.

---

## How to read this review

Findings are separated into three categories. **Downstream agents must not treat a Category C
finding as approved architecture.**

| Category | Meaning | Authority |
| --- | --- | --- |
| **A — Fidelity defects** | Real errors introduced when translating the approved architecture into Markdown. | Should be corrected to match the approved source. |
| **B — Later approved decision changes** | Places where the Markdown intentionally supersedes an older visual artifact because the human changed the decision after the diagram was approved. | Already decided. The *visual* artifact is the stale one. |
| **C — Architecture recommendations / unresolved design details** | Improvements or open questions surfaced by review. Not translation defects. | Only binding where explicitly marked **`[ACCEPTED]`**. Everything else is **`[PROPOSED]`** and awaits human decision. |

## Part 1 — Category A: fidelity defects

### A1. HIGH — invariant renumbering breaks the diagrams' own cross-references

The Runtime Flow diagram annotates its own nodes with references by number — *"rule 5 —
LookupPipeline never references PaddleOCR, Kiwi or KRDICT directly"*, *"rules 2 & 9"*, *"rules 4 & 8"*,
*"rule 6"*, *"rule 7"*. Those numbers must stay resolvable across the diagram/Markdown pair.

| Doc | Diagram count | MD count | Alignment |
| --- | --- | --- | --- |
| 01 Runtime Flow | 9 | 10 | OK — 1–9 identical; 10 appended (the correct pattern) |
| 02 Component Architecture | 10 | 12 | Broken — diagram rule 10 ("keep engine reusable") became **md rule 12**; md 10–11 are insertions |
| 03 Implementation DAG | 12 | 11 | Broken — diagram rules 04 + 05 merged into **md 4**; everything after is off by one |
| 04 Agent Execution Flow | 17 | 15 | Broken — merges plus one drop (diagram 14, "agents may edit code…", survives only as prose) |

An agent that reads the diagram, then the Markdown, will resolve "invariant 5" to two different
statements depending on which artifact it read last.

**Recommended fix — stable IDs.** Move both artifacts to prefixed, stable identifiers:

- `RF-INV-01…` — Runtime Flow
- `CA-INV-01…` — Component Architecture
- `DAG-INV-01…` — Implementation DAG
- `AEF-INV-01…` — Agent Execution Flow

Stable IDs **must preserve the mapping to the original diagram rule numbers** where one exists
(diagram rule 5 → `RF-INV-05`), so the in-diagram annotations keep resolving. Statements added by the
translation take new IDs at the end of the sequence rather than displacing existing ones — which is
exactly what `01` already does correctly and what `02`, `03`, `04` should be brought in line with.

### A2. MEDIUM — derived content is not distinguishable from approved content

Several statements in the `.md` files are correct and useful but do **not** appear in the source
diagram, and nothing marks them as derived:

- `01` invariant 10 (PaddleOCRProvider is the configured V1 implementation) — new. *(Note: this one is
  a correct expression of the later scope decision described in B1, and should be retained.)*
- `02` invariants 10 and 11 (MouseObserver / HoverController; PopupController) — new; consistent with
  the Runtime Flow diagram but not present in the Component Architecture rule list.
- `02` invariant 4 adds **SQLite** to the "UI never depends on" list (diagram names PaddleOCR, Kiwi, KRDICT).
- `02` Control Center capabilities gain *target / region selection*, *hover delay*, *hotkeys* — these
  come from the **DAG** diagram (Wave 5 D), not the Component Architecture diagram. Defensible
  cross-document synthesis, but unsourced.
- `03` Wave 10: "`GitHub Actions Build Matrix` depends on `Desktop V1 Integration` **and the packaging
  definition**", and Release Infrastructure "consumes packaging / artifact conventions" — these edges
  are inferred, not drawn. Given the doc's own rule that *"an edge in this DAG represents a real
  implementation blocker"*, an inferred edge is a meaningful addition.
- `04` "the repository and tests as the executable state of the project" — sensible addition; the
  diagram's context box lists "repository instructions" only.
- `04` invariant 15 ("wording such as *may*, *when useful* … must not be converted into mandatory
  rules") — a genuinely valuable addition for AI consumers, not in the diagram.

**Recommended fix:** a `> Derived — not stated in the approved diagram` marker inline, or a "Derived
statements" appendix per file. Downstream agents will treat every numbered invariant as approved
architecture; they need to know which ones a human signed off on in the diagram and which the
translation authored.

### A3. LOW — wording drift worth a correction pass

- **`01` step 4.** Diagram: *"Three providers initialize in parallel."* MD: *"may initialize in
  parallel."* Harmless in effect, but it converts a stated design into an option.
- **`03` invariant 2.** Diagram: *"validated before depending on desktop **UI**."* MD: *"before desktop
  **integration**."* The MD is stricter than approved. It happens to describe the drawn DAG correctly
  (Wave 4 is gated on Engine E2E), but it is a strengthening rather than a translation.
- **`DictionaryEntry` cardinality.** The DAG diagram shows `DictionaryEntry[]` (plural); `03` says
  "normalized `DictionaryEntry` data" and `02`'s contract table says `DictionaryEntry` singular. A
  Korean word routinely has more than one sense — the contract should state explicitly that lookup
  returns a collection.
- **`03` Wave 5 D gate.** "Basic Control Center exists before final hover integration" is a deliberate
  project gate, not a technical blocker. `03` labels it correctly; ensure Linear materializes it with
  that label so a future agent does not "optimize" the edge away as an unnecessary dependency.

## Part 2 — Category B: later approved decision changes

These are **not** defects in the Markdown. In each case the Markdown is current and the visual
artifact is stale.

### B1. EasyOCR — superseded scope decision, not a translation defect

The visual diagrams and the Markdown genuinely disagree about EasyOCR:

| Source | What it says |
| --- | --- |
| Runtime Flow diagram | `OCRProvider` → **PRIMARY PaddleOCR** / **ALT EasyOCR**. "Configurable alternative — only one implementation is loaded at startup. Not an automatic fallback." |
| Component Architecture diagram | `OCRProvider` implemented by **PaddleOCRProvider** and **EasyOCRProvider**; `EasyOCR ↑ EasyOCRProvider` in the external-libraries layer; pipeline note names "never on PaddleOCR, **EasyOCR**, Kiwi, SQLite…". |
| Implementation DAG diagram | Wave 2 A: "primary OCR of V1 · EasyOCR is not a V1 requirement". |
| `01`, `02`, `03` (Markdown) | EasyOCR absent; `PaddleOCRProvider` is the configured V1 OCR implementation. |

**Decision history.** The original diagrams were approved with EasyOCR as an alternative OCR
implementation. *After* that approval, the human explicitly changed V1 scope. The current approved
position is:

- `OCRProvider` remains an abstraction;
- `PaddleOCRProvider` is the **only** V1 OCR implementation;
- EasyOCR is **not** part of V1;
- EasyOCR may or may not be reconsidered later;
- `HanlyOCRProvider` or another provider may eventually implement the same seam.

**Therefore the Markdown is correct and EasyOCR should not be restored.** The provider abstraction
remains valid and worth keeping with a single V1 implementation — it exists to keep `LookupPipeline`
independent of any concrete OCR library and to leave room for a future provider, not to serve a
count of live implementations.

**Action:** annotate the three visual artifacts so downstream agents know their EasyOCR references
are superseded by the later textual decision, and update the diagrams when they are next revised.
Until then, an explicit note in the Markdown (e.g. in `02`, near the adapter table) stating that
*"the approved diagrams predate the V1 scope decision and still show an EasyOCR alternative"* will
prevent an agent from "restoring" it as a perceived omission — which is precisely the mistake the
first version of this review made.

**One residual item to keep consistent:** `ConfigManager` and the Control Center still expose "OCR
provider selection" / "current OCR provider". That wording should not imply that V1 ships multiple
selectable implementations. Either present it as read-only status ("current OCR provider:
PaddleOCR") or keep it as an explicitly forward-looking extensibility point — but state which was
intended, so a downstream agent does not build a selector with one option or delete a seam that was
meant to stay.

### B2. Hover delay range — minor documentation inconsistency

The Runtime Flow diagram records `≈ 80–200 ms`; the DAG diagram records `≈ 80–250 ms`. Both
Markdown files detected the conflict and flagged it rather than silently reconciling it, which was
the right behavior.

**Approved interpretation:** the delay is **configurable**; roughly **80–250 ms** is an initial
experimental range; exact useful values will be tuned empirically. This is a wording inconsistency
to normalize, not a material architecture problem. Both documents should state the range as
experimental and the value as configurable, and drop the open-clarification callout once normalized.

## Part 3 — Category C: architecture recommendations and unresolved details

Items marked **`[ACCEPTED]`** have been approved by the human and should be reflected in the
Markdown architecture. Items marked **`[PROPOSED]`** are review output only and are **not** approved
architecture.

### 3.1 What the architecture gets right

Worth restating, because none of the below changes it:

- Clean ports-and-adapters split with a genuinely unidirectional package rule. `hanly` stays
  reusable, and the diagrams resist speculative browser/CLI modules — correct discipline.
- `LookupController` (app runtime state) vs `LookupPipeline` (engine orchestration) is the single
  most important distinction in the design, and both the diagram and `02` state it explicitly.
- `ResourceManager` (understands resources) vs `UpdateService` (obtains resources) is a split most
  projects get wrong, protected by the "engine must function without GitHub Releases" invariant.
- UI-thread discipline, ROI-over-full-screen capture, and stale-request handling are the three things
  that determine whether a hover dictionary feels good. All three are first-class.
- Manual hotkey lookup before automatic hover is correct sequencing: it proves the whole desktop
  stack with a deterministic trigger before adding timing-sensitive behavior on top.
- The HanlyOCR research track is correctly fenced off as non-blocking and evidence-driven.

### C1. `[ACCEPTED]` `LookupResult` must model normal non-success outcomes

The hover flow branches on exactly two conditions: *cursor still valid?* and *request still current?*
There is no path for the ordinary, expected outcomes: OCR returns nothing; the recognized text is not
Korean; `WordResolver` cannot pick a segment; morphology yields no lemma; the dictionary has no entry;
confidence is too low. `LookupResult` is described only as "everything the popup needs to present",
so today every one of these becomes an exception or a silent nothing at the popup boundary.

**Accepted requirement:** `LookupResult` must conceptually distinguish

- **success** — a usable lookup;
- **empty / not-found / unusable** — the pipeline ran correctly and there is nothing to show;
- **processing error** — something actually failed;
- optionally, **partial or diagnostic data** carried alongside any of the above.

This belongs to Wave 1 `Core Contracts`, since it is the seam every UI and every future client
consumes. The concrete Python design is deliberately left open — this review does not prescribe a
result type, enum shape, or exception policy.

### C2. `[ACCEPTED]` Desktop lookup execution must be bounded / latest-wins

Request currency is validated only *after* the full pipeline completes. With a hover delay in the
80–250 ms range and OCR inference plausibly exceeding it, a user sweeping the cursor across a line
can enqueue jobs faster than they drain, and each one runs to completion before being discarded.

**Accepted requirement:** desktop lookup execution must be **bounded and latest-wins**, so stale
hover jobs cannot accumulate without limit. This belongs in the `Desktop Foundation` (Wave 4)
acceptance criteria.

Constraints on the resolution:

- no specific Python concurrency framework is prescribed;
- cooperative cancellation between pipeline stages is **allowed and encouraged where practical**, but
  is not mandated as the mechanism;
- final request-currency validation immediately before popup presentation **remains required** for
  correctness regardless of what bounding or cancellation strategy is chosen.

### C3. `[ACCEPTED]` ResourceManager / provider / composition boundary — chosen resolution

The Component Architecture diagram says `ResourceManager` is *"used by the engine and providers to
locate required resources"*, while the DAG says `ResourceManager Core` is **not** a dependency of
`LookupPipeline` and sits on a side track parallel to Wave 2 A–E. Read literally, both cannot hold if
`PaddleOCRProvider` / `KRDICTProvider` reach into `ResourceManager` to find their model and database.

**Approved resolution:**

- `ResourceManager` locates, validates, and understands local resources.
- Composition / application wiring obtains validated paths and configuration from `ResourceManager`.
- Concrete providers receive **explicit resource paths / configuration** at construction.
- Providers therefore do **not** depend directly on `ResourceManager`.
- `LookupPipeline` remains independent of `ResourceManager`.
- Consequently the DAG is correct to keep `ResourceManager Core` outside the `LookupPipeline`
  blocker path.

This also keeps Wave 2 adapters unit-testable against fixture paths. `02`'s phrasing — "provides
paths and `ResourceMetadata` to engine adapters" — should be updated to reflect that the composition
root is the consumer, not the adapters themselves.

### C4. `[ACCEPTED]` Two early, non-blocking risk-reduction spikes

Both are **risk-discovery work**, explicitly **non-blocking**, and explicitly **not** a redesign of
the V1 critical path:

1. **UI threading / lifecycle spike.** PyQt6 and pywebview both want the main thread, and on macOS
   that is a hard constraint. The design runs both plus a worker, and no document names which thread
   owns the main loop. Probe the PyQt6 + pywebview + worker/main-thread interaction, macOS first.
2. **Packaging feasibility spike.** Wave 10 is currently the first point at which PyInstaller meets
   PaddlePaddle wheels across three operating systems — a combination that is large and historically
   fragile. A minimal PyInstaller + PaddleOCR/PaddlePaddle packaging exploration on the target OSes
   surfaces the constraint while it is still cheap to react to.

Discovering either constraint at Wave 9–10, after integration and polish, is the highest-variance
risk in the current plan; both spikes exist to move that discovery earlier without reordering the
critical path.

### C5. `[ACCEPTED]` Architecture changes require explicit human approval

`04` establishes the human as the authority for ecosystem selection, acceptance, and commit/merge,
but says nothing about who may change `01`–`04` themselves. Since these documents are the input to
every future plan, silent agent edits would propagate.

**Approved rule:**

- agents **may** identify and propose architecture changes;
- changes to architecture source-of-truth documents **require human approval**;
- agents **may** draft changes or ADRs when asked;
- commit/merge authority remains governed by the existing separate rule in `04`.

### C6. `[ACCEPTED]` Korean implementation test fixtures

Wave 2 A/B/C acceptance criteria are behavioral, but nothing in the DAG produces the small set of
deterministic Korean inputs needed to accept them. The HanlyOCR track's step 1 ("benchmark dataset")
is the natural home for a large evaluation corpus, but it is marked future and non-blocking — and it
is not what this item is.

**Accepted:** a small `Korean Test Fixtures` capability in Wave 1/2, consumed by A, B, C, and D.

Scope is **only** a small set of deterministic development/test fixtures used by the normal automated
`tests/` suite, such as:

- a few Korean OCR image / ROI samples;
- morphology cases;
- dictionary cases;
- `WordResolver` bounding-box / cursor cases.

Explicit non-goals — this is **not**:

- a large dataset;
- a benchmark framework;
- a HanlyOCR training or evaluation corpus;
- new dataset infrastructure;
- a large standalone subsystem.

The purpose is simply reproducible unit and integration testing, and shared regression inputs across
the Wave 2 branches.

### C7. `[PROPOSED — evidence-driven, defer]` Latency measurement before any latency target

No latency target appears in any of the four diagrams, while the hover delay is explicitly "to be
validated empirically" and `V1 Validation` lists "lookup latency" as an area.

Deliberately **not** recommending a frozen number at this stage. Recommend instead:

1. instrument the pipeline so per-stage timings are observable from Wave 3 onward;
2. validate hover timing empirically against real usage;
3. define a performance target **after** representative measurements exist.

### C8. `[PROPOSED — profiling-driven, defer]` Caching as a possible optimization

Hovering the same word twice currently re-runs OCR, morphology, and the SQLite lookup. An ROI-hash →
`OCRResult[]` cache and a lemma → `DictionaryEntry` cache are the obvious candidates if measurement
shows they are needed.

Explicitly classified as: **profiling-driven**, **not an architectural requirement**, and **not
required before Wave 2**. Do not add caching to the contracts speculatively.

### C9. `[PROPOSED]` Coordinate spaces — real risk, resolution deferred

Multi-monitor layouts, Windows fractional DPI scaling, and Retina backing scale all mean that a
cursor position in screen coordinates is not the same as a pixel position inside the captured ROI.
`WordResolver` consumes "cursor context" inside the engine, so the mapping touches the engine seam.

The useful architectural principle to carry now:

> The reusable engine should consume image/ROI-relative context rather than raw OS-specific screen
> coordinates.

That principle also keeps the engine honest for a future browser client, where "cursor context" is a
DOM position rather than a screen pixel. The **detailed** DPI / multi-monitor transform design is
deliberately not specified here; it must be resolved before `CaptureService` and desktop integration
mature, not before Wave 2 engine provider work begins.

### C10. `[PROPOSED]` KRDICT redistribution and attribution must be verified before shipping

Wave 8/10 ship processed KRDICT data through GitHub Releases. This review makes **no legal
conclusion**. It states only that the redistribution and attribution terms attached to the source
dictionary data need to be verified before processed dictionary artifacts are distributed —
preferably before Wave 2 C fixes a distribution format, since that is where the cost of a change is
lowest.

## Part 4 — Recommended action order

1. **Mark the EasyOCR references in the visual artifacts as superseded** by the later V1 scope
   decision. Do **not** restore EasyOCR to the Markdown. *(B1)*
2. **Introduce stable invariant IDs** (`RF-INV-*`, `CA-INV-*`, `DAG-INV-*`, `AEF-INV-*`), preserving
   the mapping to original diagram rule numbers so in-diagram cross-references keep resolving. *(A1)*
3. **Distinguish derived Markdown statements** from directly approved diagram statements. *(A2)*
4. **Apply the approved ResourceManager / composition resolution** to `02` and confirm `03`'s
   dependency wording. *(C3)*
5. **Extend `LookupResult` contract semantics** to cover normal non-success states, in Wave 1
   `Core Contracts`. *(C1)*
6. **Add bounded / latest-wins lookup execution** to the `Desktop Foundation` acceptance criteria,
   retaining final request-currency validation before presentation. *(C2)*
7. **Add the two early non-blocking spikes** — UI threading/lifecycle and packaging feasibility. *(C4)*
8. **Add the accepted small Korean implementation test fixtures** for Wave 2 acceptance — a handful of
   deterministic OCR/morphology/dictionary/`WordResolver` cases in the normal `tests/` suite, not a
   dataset, benchmark framework, or new infrastructure. *(C6)*
9. **Add explicit human governance** for changes to architecture source documents. *(C5)*
10. **Normalize hover-delay wording** as configurable with an initial experimental range of roughly
    80–250 ms, and retire the open-clarification callout. *(B2)*
11. **Leave fixed latency targets, caching, and detailed coordinate transforms** to later
    evidence-driven planning. *(C7, C8, C9)*
12. **Verify KRDICT redistribution / attribution terms** before distribution decisions are locked in. *(C10)*

Plus the low-severity wording pass from A3 whenever the files are next edited.

## Closing

The architecture does not need to be redrawn from scratch. The package boundaries, the
engine/client split, and the responsibility assignments are strong, and the sequencing decisions —
engine validated before desktop, manual lookup before hover — are the right ones.

What remains is contract semantics (`LookupResult`), concurrency policy (bounded execution),
platform risk (threading and packaging), documentation fidelity (invariant IDs, derived-content
marking, superseded diagram annotations), and a small amount of early implementation-risk reduction.

**Nothing in Category C is approved architecture unless it carries an `[ACCEPTED]` marker.**
Downstream agents should treat `[PROPOSED]` items as input to a future human decision, not as
requirements.
