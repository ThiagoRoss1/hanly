## 1. Decision summary

- One `Hanly-vX.Y.Z.hup`: a bounded ZIP containing JSON metadata and manifests,
  **no application payload**. One shared planner and verifier in `hanly_app`.
- At most one direct file-level delta per published OS/architecture, against
  the preceding compatible published build. No chains or binary patch algorithm.
  Separate release assets mean a client fetches only its platform's payload.
- Windows retains selective staging and the working PowerShell in-place
  transaction. macOS and Linux construct a complete private candidate from
  verified reusable content plus changed files, then replace the whole root.
- macOS uses the published signature bytes, preserves bundle metadata and links,
  and verifies the reconstructed bundle. Never re-sign on the user's machine.
- Full fallback: existing Windows ZIP, macOS DMG, Linux tar.gz. Keep existing
  lowercase `hanly-desktop-*` public names; use display labels for “Hanly for
  Windows/macOS/Linux.” Renaming downloads buys little and breaks old clients.
- Keep application and resource versioning independent. KRDICT and
  `hanly-resources.json` stay on the same GitHub release for MVP.
- Keep legacy assets on **every release reachable by supported pre-HUP clients**.
  One bridge release cannot teach a client that skips it a new protocol.
- Retain GitHub/HTTPS trust plus digest verification. No new publisher signing
  key in MVP; ad-hoc codesigning is not publisher authentication.

## 3. HUP v1 wire contract

### Container

`Hanly-v<MAJOR.MINOR.PATCH>.hup` is a ZIP using stored/DEFLATE members only:

```text
index.json
manifests/windows-x86_64.json
manifests/macos-arm64.json          # example: only architectures actually built
manifests/linux-x86_64.json
```

No nested archives, scripts, resource bytes, delta bytes, filesystem links,
encrypted members or ZIP64. Read metadata in memory within bounds; never
extract HUP paths onto the filesystem. Filename must match pinned release tag.
Index owns the list of manifest members; reject missing, duplicate and extra
members. Do not put the HUP's own hash inside itself.

Initial hard limits, shared producer/consumer constants: 16 MiB HUP compressed,
64 MiB total expanded, 8 platform entries, 9 ZIP members, 256 KiB index,
8 MiB per manifest, 100,000 entries per manifest, 32 JSON nesting levels,
4,096 UTF-8 bytes per path/link target, 256 bytes per release asset name.
Reject duplicate JSON keys, invalid UTF-8, booleans where integers are expected,
nonfinite numbers and unknown schema versions. Bounds apply while reading,
not after unbounded decompression. Increase only with measured release evidence.
No blanket compression-ratio rejection for legitimately compressible metadata;
absolute expansion limits are the guard.

### Index and descriptor

Illustrative JSON (angle-bracket values denote generated values, not literals):

```json
{
  "hup_version": 1,
  "product": "hanly-desktop",
  "release": {"tag": "vX.Y.Z", "version": "X.Y.Z", "source_commit": "<40 hex>"},
  "platforms": [{
    "platform": "macos",
    "architecture": "arm64",
    "identity": {
      "product": "hanly-desktop", "platform": "macos", "architecture": "arm64",
      "version": "X.Y.Z", "build_id": "<build UUID>"
    },
    "manifest": {"member": "manifests/macos-arm64.json", "size": 12345, "sha256": "<64 hex>"},
    "full": {"name": "hanly-desktop-macos.dmg", "format": "dmg", "size": 123456, "sha256": "<64 hex>"},
    "delta": {
      "base_identity": {"product": "hanly-desktop", "platform": "macos", "architecture": "arm64", "version": "<base>", "build_id": "<base UUID>"},
      "base_manifest_sha256": "<64 hex>",
      "payload": {"name": "hanly-desktop-macos-arm64-from-<base>-to-X.Y.Z.delta.zip", "format": "files-zip-v1", "size": 1234, "sha256": "<64 hex>"},
      "changed_paths": ["Contents/MacOS/hanly-desktop"],
      "deleted_paths": []
    },
    "layout": {"root": "Hanly.app", "executable": "Contents/MacOS/hanly-desktop"},
    "macos": {"bundle_identifier": "io.github.thiagoross1.hanly", "signature_policy": "adhoc-v1"}
  }]
}
```

`delta` is null when absent, with a bounded `delta_omitted_reason`. No array of
chains or script instructions. Changed/deleted paths are sorted, unique and
must equal the diff of the named base and target manifests. This is explicit
payload coverage, not authority to delete anything in a live installation.
Directories/link-only changes can have an empty content ZIP. Omit a delta when
its compressed payload is no smaller than full; disclose the full size.

Platform names: `windows`, `macos`, `linux`. Architectures: `x86_64`, `arm64`;
add no architectures in this wave. Use the **running frozen build's** stamped
architecture, including x86_64 under Rosetta, not physical host CPU selection.
Unsupported tuple means no automatic install, with human-download guidance;
never select a foreign architecture as fallback. Freeze explicit runner/target
architecture in build.yml and verify actual executable architecture agrees.
No architecture switch or universal2 assembly is included.

Each asset name resolves uniquely inside the pinned GitHub release's asset
list. Index contains no arbitrary URL or repository override. Bind release ID,
tag, asset IDs, names, API sizes and available digests into `PreparedUpdate`;
all subsequent downloads use that snapshot. A refresh must not silently alter
an approved plan. Missing/mismatched descriptor data is an error, not permission
to download a different asset.

### Manifest v2 and identity without signing recursion

Keep V1 parser/serializer semantics unchanged for legacy Windows exports.
Introduce `schema_version: 2` tree manifests with `identity`, `layout`, and
sorted `entries`. Each entry has `path`, `kind` (`file`, `directory`, `symlink`),
`component`, and platform metadata:

- File: exact `size` and SHA-256. POSIX also has exact permission bits.
- Directory: include empty directories and POSIX modes. Root metadata is in
  `layout`; no ambiguous `.` entry.
- Symlink: exact relative `link_target`; never follow it while inventorying.
  Its target text participates in identity. Do not chmod through links.
- macOS: bounded map of allowlisted material extended attributes to base64
  bytes on the corresponding entry (max 64 KiB/value, 1 MiB/manifest). Record
  signing attributes such as `com.apple.cs.*` if present. Reject unsupported
  material metadata during production rather than silently dropping it.

Manifest serialization: UTF-8, sorted keys, compact separators, entries sorted
by exact path, no insignificant newline; SHA-256 over these canonical bytes.
The index hash must also match the member's actual bytes. Exact target identity
is **BuildIdentity plus full manifest SHA-256**, never version or UUID alone.

Allocate a fresh build UUID **before freezing**, record source commit and actual
architecture, and embed a small `hanly-build.json` as package data (under
`hanly_app` assets, read through package resources). Reusing a frozen artifact
reuses its UUID; rebuilding allocates a new UUID even for the same tag. The UUID
is an identifier, not a content hash. This replaces only the V2 build-id meaning;
legacy V1 still uses its existing content fingerprint.

Generate V2 manifests **after all signing and final tree changes**, outside the
application. Do not write a self-describing post-sign manifest into `Hanly.app`:
that would change the seal and create a circular manifest/signature dependency.
Store installed V2 manifests/receipts under a per-user, per-installation directory
(`updates/<hash-of-canonical-install-path>/`), with build stamp, manifest digest,
release provenance and preserved-path inventory. Persist only verified data.

Fresh full/manual installations have the stamp but no receipt. On the first
update preparation fetch their **installed tag's** HUP (bounded extra metadata),
require exact stamp identity, and hash/inspect the actual tree before admitting
reuse or ownership. If unavailable, do not manufacture ownership: offer safe
manual migration or the constrained clean-tree bootstrap described below.
Normal launch stays offline; no HUP fetch is required just to open Hanly.

Windows builds additionally write the legacy `.hanly-manifest.json` before
archiving. Build order is stamp → freeze → V1 installed manifest → V2 external
manifest → archives/deltas → HUP. V2 explicitly owns this legacy control file;
V1 continues excluding itself. Allow it only as this recognized control entry,
never by relaxing all updater-reserved paths. This ordering is acyclic.
The new Windows transaction updates this control entry and external V2 receipt;
the legacy helper may leave an old V1 inventory, so bootstrap relies on the
new embedded stamp and verified published HUP, not that stale file.

### Payload and path policy

Use the same `files-zip-v1` delta format on all OSes: regular-file bytes at
manifest-relative paths, no archive symlinks, permissions or executable actions.
Only content-new/content-changed files need bytes. Modes, directories, link
creation and allowed macOS xattrs are taken from manifests. Signature resources
are ordinary hashed target files; changed Mach-O binaries are copied in full.
Never regenerate `CodeResources`, signatures or executable signatures locally.

Metadata-only changes still count as changes; unchanged bytes may be reused only
after hashing. For safety, producer and client derive required byte members from
the two manifests and check the explicit lists. Deletions come from verified
base ownership. A delta is usable only if every needed byte is either verified
reusable content or present in its payload. A damaged unchanged file missing
from the delta requires an explicitly confirmed full fallback.

Reject absolute/drive/UNC paths, NUL/control characters, backslashes, empty or
`.`/`..` path segments before normalization, duplicate names and parent-file
shadowing. Preserve exact Unicode spelling. Windows adds ADS/device/trailing
space-dot/case-fold/reparse restrictions. macOS rejects case and Unicode
normalization aliases conservatively, even on a case-sensitive volume. Linux
can retain distinct case but all paths must remain representable and contained.
POSIX permits internal relative symlinks, including `..` in **link targets**
only when graph resolution remains inside the root. Reject cycles, dangling
links, absolute links and a material path descended through a symlink. Create
real files/directories before links. No hardlinks, sockets, devices, FIFOs,
setuid/setgid bits, capabilities, ACL import or foreign ownership changes.

Full extractors also preflight member counts/types, duplicated/aliased paths,
parent conflicts and declared expanded sizes. Do not call unbounded getmembers
or trust a ZIP directory list of arbitrary size. Stream with global limits
(100,000 entries, at most 8 GiB expanded product for MVP) and exact per-file
limits. Recheck containment/no-follow handles at each write/copy boundary.
Full Windows prefix is `hanly-desktop/`; Linux uses that same root; DMG contains
`Hanly.app`. Do not accept a delta as a full archive by guessing its prefix.

## 4. Release contract and bootstrap migration

### B: first HUP-aware bridge release

Publish these exact existing products and compatibility assets:

| Asset | Purpose |
|---|---|
| `hanly-desktop-windows.zip` | Human product and both generations' full Windows source |
| `hanly-desktop-macos.dmg` | Human product and HUP macOS full fallback |
| `hanly-desktop-linux.tar.gz` | Human product and both generations' full Linux source |
| `Hanly-v<B>.hup` | New common application index, all produced target manifests |
| `hanly-desktop-windows.manifest.json` | Unchanged V1 wire contract for old Windows clients |
| `hanly-desktop-windows.update.json` | V1 metadata pointing to the **current B** manifest/full ZIP |
| `hanly-desktop-macos.zip` | Exact current B `.app` via ditto for old macOS clients |
| `SHA256SUMS` | Hashes for all explicit assets except itself, including HUP and resource pair |
| `hanly-resources.json`, one `krdict-<resource-version>.sqlite3.zst` | Independent resource delivery |
| Optional per-platform delta assets | Only when a verified compatible predecessor exists |

For simplicity, the compatibility Windows update.json is **full-only**, with a
clear reason and no legacy delta descriptor. Old clients already support this
branch and ask about full size. Do not publish a second, legacy-only delta to
save one bootstrap download. New HUP clients use the new delta assets.
Normally B has no V2 predecessor and publishes no HUP delta; B+1 can delta
from B. It is acceptable that the first transition costs a full download.

### Migration matrix

| Installed client | How it reaches B or any later HUP release |
|---|---|
| Working pre-HUP Windows differential client | Fetches the legacy sums/update/manifest, confirms full ZIP, stages through its old helper, launches target. New target answers **legacy version-text ack**. Its next prepare uses HUP and establishes V2 receipt from its installed tag. Do not require the old helper to understand V2 metadata. |
| Pre-HUP macOS `.app` client | Its current whole-bundle path downloads legacy ditto ZIP and swaps. Target answers old ack. Subsequent updates use HUP/DMG or delta. |
| Pre-HUP Linux directory client | Existing tar.gz and old swap/ack; subsequent HUP preparation bootstraps receipt. |
| Windows 0.5.0/0.5.1 with known broken exit | Existing documented manual replacement remains necessary. A target cannot fix the running old updater. Preserve path/user data; recommend backing up the old root and installing a clean target, reconciling user extras explicitly rather than blind overwrite. |
| macOS 0.1.1 plain-directory/tar client | Existing documented one-time DMG/manual migration remains; do not resurrect the retired macOS tar format. |
| HUP-aware client skipping releases | Latest target HUP; unmatched direct delta base means size-confirmed full current platform product. No hop chain. |
| Unknown/unowned installation | No destructive automatic adoption. Verify an exact published old inventory if available; otherwise block and provide manual clean replacement preserving the old directory. |

The pre-HUP migration retains the old helper's guarantees and limitations for
that one update. Do not promise new transaction/identity guarantees before the
HUP-aware client actually runs. A legacy full update of a modified install is
not retroactively made safe by HUP; bridge notes warn users to preserve extras.

### Retention, skipped bridge, and eventual clean steady state

**B, B+1, and every later release keep the compatibility assets above while
pre-HUP clients remain supported.** Latest-only old clients that skip B update
directly to the current build using those assets. Never point legacy metadata
to B's bytes under a later version: old helpers expect the latest version ack.
Never rely on release notes, HUP redirects, download statistics, a time window,
or keeping B in the release archive to redirect an unmodified old client.

There is **no finite safe retirement release under the stated no-stranding
requirement**. Thus the operative MVP steady state remains HUP plus the three
compatibility assets and SHA256SUMS. Keeping the macOS ZIP is a compatibility
cost, not a format requirement of the HUP installer.

A future clean-only layout is three full products + one HUP + zero to three
deltas + resource pair + SHA256SUMS + GitHub automatic source archives. It can
start only at an explicitly approved release `R` that ends automatic support
for pre-HUP clients and supplies a manual upgrade route. Under current scope,
**R is unset and retirement is disabled**. Removing legacy Windows documents
would make old Windows prepare fail; removing macOS ZIP would make old macOS
report outside-app updating. If Thiago continues to require no newly stranded
installations, do not set R. No new hosting/latest-channel machinery in MVP.

Historical no-op validation must classify older release sets by protocol era,
not require HUP on already-published pre-B releases. New releases must not pass
by using the historical allowlist. Derive an exact expected asset set from the
validated HUP and compatibility policy; no arbitrary glob publication. GitHub's
automatic source archives are links, not items in its explicit assets array.

contracts, never the reverse. Keep the existing prepare/install/abandon port;
no generalized updater framework or extensible state machine.

## 6. Platform staging and installation

### Windows: adapt, do not rewrite

WinForms courtesy progress and external recovery copy.

Before mutation recheck every operation's expected kind/hash and no-follow
parents; reject concurrent content changes instead of overwriting them. Verify
reused target content as well as staged changes so success names the exact
managed target. A full ZIP is still only a source for required files, not a
whole-tree Windows swap. Unknown extras are preserved; every newly claimed
path, including same-content occupants, requires known ownership or an explicit
safe bootstrap, not “equal bytes means ours.” Refuse unsupported file/directory
or case-only transitions with a manual replacement explanation in MVP rather
than guessing destructive ordering.

Stage the target legacy control manifest as an explicit special operation, and
persist target V2 receipt only after target verification/ack. Keep previous
receipt/control file for rollback. This closes the stale installed-inventory
problem instead of assuming `_unpack` includes reserved metadata today.

Windows free-space requirement is payload + new staged bytes + bounded metadata
and logs + 256 MiB margin. Existing files renamed to backup are already
allocated; do not count them again. Different-volume copy optimizations are not
supported. Keep recovery per installation so two Hanly copies do not overwrite
one shared pending pointer. Preserve readable V1 pending transactions until
settled by their original recovery helper; never reinterpret them as V2.

### macOS: reconstruct exact published `.app`

1. Refuse automatic apply from a mounted DMG, translocated/read-only install or
   non-writable parent. Ask for a normal installation location through an
   actionable error; no privilege escalation or Gatekeeper bypass.
2. Resolve base stamp/receipt/published manifest and inspect without following
   links. Verify the installed bundle signature before using it as a delta base.
   Failure means a full candidate may be offered with size confirmation.
3. Create a private sibling transaction on the **same volume**. Reconstruct a
   fresh candidate in manifest order from verified base files plus delta bytes.
   Use independent copies first; no hardlinks into the running installation.
   Do not blindly copy arbitrary local bundle contents into the target.
4. Recreate exact links/modes and material xattrs, including published signature
   files and any target signing attributes. Keep local provenance attributes
   (quarantine/Finder/application-instance metadata) separate from content
   identity. Preserve quarantine provenance; never blanket `xattr -cr` or
   remove quarantine to force launch. Clean CI products must not require ACLs,
   FinderInfo or resource forks; fail producer checks on unsupported metadata.
5. Exact target tree comparison includes every real entry, link, mode, allowed
   material xattr and file hash. Require expected plist identifier, both version
   values, executable path/architecture and build stamp. Run
   `/usr/bin/codesign --verify --deep --strict --verbose=2 <candidate>` with
   bounded execution/output and fail on nonzero exit. This verifies nested code
   as well as the envelope; it does not establish a Developer ID trust chain.
6. Flush staged data/metadata, hand off to the POSIX transaction helper, wait for
   all old app processes, swap at the same path, relaunch via `/usr/bin/open`
   with explicit new-instance semantics, then await exact startup acknowledgement.

No unmanaged content may be discarded when deleting the old bundle. If real
unexpected files/material metadata exist inside `.app`, stop automatic install
with listed paths and an instruction to move them out or keep the old bundle
through manual replacement. Expected per-machine non-content xattrs are not
unmanaged product files. The same rule applies to delta and DMG fallback.
Fallback does not override a collision or bundle-ownership failure.

APFS clonefile/reflink reuse is deferred: ordinary bounded copies give correct
rollback on all supported filesystems. A later optimization may use copy-on-write
clones, but must retain conservative free-space accounting and never mutate
shared hardlink inodes. The goal here is reduced network delivery, not zero
local writes.

### macOS full fallback: use the existing DMG

Source establishes that DMG and legacy ZIP originate from the same finished
bundle. HUP clients may safely use the DMG **after implementing** these boundaries:
verify outer exact size/hash first; attach read-only/nobrowse at a private empty
mountpoint using `hdiutil ... -plist`; parse bounded plist to bind the actual
device and mounted path; impose timeout and reject unexpected/encrypted/multi-
volume layouts. Locate exactly the real `Hanly.app` root, validate its shape,
copy via `/usr/bin/ditto` to staging with links/permissions/material metadata,
and run the same exact manifest and codesign checks. Never launch from the
mount. Detach the actual owned device in finally on success/error/cancel; retain
an actionable cleanup record if unmount fails, without force-unmounting unrelated
volumes. Candidate readiness requires the acquisition step to settle.

Release validation must compare the DMG-extracted candidate to the producer's
post-sign manifest and, during compatibility retention, the ZIP-extracted tree.
The existing executable-presence smoke alone is insufficient evidence. DMG becomes
the runtime fallback at B; deleting its duplicate ZIP remains governed by §4.

### Linux: reconstruct then directory swap

Use the same candidate builder and POSIX transaction as macOS, without bundle
signing or DMG code. Preserve onedir layout, execute/read bits and relative
library links; validate the build stamp, executable ELF architecture, exact
managed target entries and bytes. Full tar.gz passes the same validation after
bounded extraction. No local package-manager ownership or sudo handling.

For non-conflicting unmanaged regular files/directories and contained symlinks,
copy them into the candidate under a separate preserved-path inventory, keeping
bytes/modes and no-follow safety; account for their space. They never become
product-owned merely by surviving a swap. Block collisions, unsupported special
files/ACLs/capabilities and file-directory transitions involving extras. For an
unowned pre-manifest tree, automatically bootstrap only if it exactly matches a
verified published manifest; otherwise use manual clean replacement preserving
its old root. Recheck extras after old processes exit; changes invalidate the
candidate rather than silently lose user writes.

POSIX permits renaming loaded binaries, but later dlopen/import/file opens can
observe mixed versions if individual files change live. A whole candidate and
old-root backup make rollback simpler and share the existing POSIX strategy.
Waiting for the shell **and both children** remains mandatory despite rename
permissiveness. This supersedes the old plan's suggestion that Linux needs no
stop-the-app phase.

### Disk and cancellation on POSIX

Estimate additional free bytes on the installation volume as payload + complete
candidate regular bytes + copied unmanaged bytes + bounded metadata/logs +
256 MiB margin. Do not add the already-allocated old tree again for its rename
to `previous`. Avoid a second full extracted tree: extract/copy directly into
the private candidate. DMG file and copied candidate coexist; mounted image
size is not another allocated full copy. No assumed APFS space savings.

Check permission/device/space before payload and again before handoff. Cancellation
is cooperative through metadata, hashing, download, copy, extraction, signature
verification and mount cleanup. Once helper ownership is accepted, UI marks
noncancellable and quits; only helper recovery may alter that transaction.

## 7. Transactions, durable recovery and acknowledgements

Shared conceptual phases:

```text
prepared → staged-and-verified → helper-owned → waiting-for-exit
  → applying → awaiting-startup → committed → cleanup
                       failure → rolling-back → restored
                                            → recovery-required
```

A stage result is never success. Write immutable plan and verified staging
records before launching a helper. Record intent before mutation; recovery
observes actual filesystem state to handle a crash between a rename and its
completion record. Keep original data until a durable committed outcome exists.
Cleanup failures leave a committed-but-cleanup-pending result; never relabel an
installed working target as failed merely because old scratch could not be removed.

### Minimum POSIX machinery

The current temporary shell script cannot supply durable filesystem barriers,
robust locking and exact process identity by itself. Add **one small shared
POSIX native helper**, built for macOS/Linux from
`packaging/updater/hanly-update-posix.c`. C11 with only system libraries
(libc; macOS libproc/libSystem), no Python, Qt, bundled interpreter, third-party
JSON library or updater download client. It performs fixed whole-root
transactions only: claim/lock, wait, durable rename, launch, ack, restore.
It is not a file-diff engine, archive parser, privileged service or second
Hanly desktop entry point. Compile as a packaging step and include its signed
macOS binary before final bundle signing; copy it to external recovery storage
and verify that copy before handoff.

Python writes the shared diagnostic `plan.json` plus a tightly specified native
handoff descriptor: magic/version followed by a fixed number of length-prefixed
UTF-8 fields (big-endian u32 lengths), maximum 64 KiB overall and 4,096 per path.
Fields: transaction ID, canonical install/staging/backup/rejected paths,
installation device/inode, candidate device/inode, platform, relative executable,
expected ack bytes, parent PID/start identity, timeout values. Hash and bind the
descriptor in the private recovery record; no remotely provided scripts or
shell-evaluated fields. Helper rejects trailing fields, malformed lengths,
foreign ownership, link roots, mismatched device/inodes and paths outside the
predeclared transaction. It receives arguments as argv, never shell interpolation.

Keep the native descriptor local and private; it is not another release protocol.
The shared JSON plan remains the diagnostic/source representation. Unit tests
round-trip the descriptor against the native reader. This small fixed reader
avoids embedding a general JSON framework just for two rename operations.

POSIX layout:

```text
<install-parent>/.hanly-update-<tx>/
  plan.json, descriptor, candidate/, previous/, rejected/, ready, result
<per-user-updates>/<install-key>/
  lock, pending.json, verified-helper, Recover-Hanly-update launcher
  installed-receipt.json, manifests/<digest>.json
```

Use owner-only storage, exclusive creation and no-follow checks. Lock is keyed
to canonical installation and protected by OS advisory locking; transfer to the
helper without an unlocked mutation window. Register all app shell/child process
identities; use `/proc` executable/start information on Linux and native process
path/start information on macOS, rather than name/regex matching. Track children
and reject inspection failure. All app launches consult pending recovery before
ordinary initialization. A helper-launched valid ack candidate is admitted;
another launch cannot spawn a competing helper. Revalidate PID identity before
signalling; never kill unrelated same-name processes.

Native durability uses fsync of prepared files and relevant directory entries,
rename operations within one filesystem, and platform-supported stronger file
flush on macOS where appropriate. Abort before mutation if the required barriers
or same-volume semantics are unavailable. State hardware/filesystem durability
limits honestly; neither journaling nor fsync is a universal power-loss guarantee.

### POSIX recovery decision table

Each state below requires matching recorded inode/identity and private ownership;
unexpected combinations mean `recovery-required`, no deletion or speculative
launch. Default interrupted uncommitted swaps to rollback rather than retrying
an unknown candidate automatically.

| Observable state | Safe action |
|---|---|
| Old install present; verified candidate staged; no previous | No live mutation yet; abandon or retry after preconditions |
| Install absent; old root at previous; candidate staged | Restore previous to install, flush parent, report restored |
| Target at install; previous present; no valid durable commit | Stop candidate and children; move target to rejected; restore previous |
| Install absent; previous and rejected present | Finish interrupted restore by renaming previous back |
| Old root restored; rejected present; rollback record incomplete | Validate old identity, durably mark restored; then cleanup |
| Durable committed result and matching target | Retain target, retry cleanup; never rollback because cleanup failed |
| Missing/conflicting roots or failed restore | Keep every copy and external recovery launcher; launch nothing |

The install path is temporarily absent between two renames. Do not describe this
as atomic whole-tree exchange or promise that the normal app shortcut repairs a
missing executable. The external verified helper/launcher is the recovery route
after reboot if Hanly cannot run. Recovery must require no downloads and no file
from either root. Windows retains its per-file recovery and analogous ownership
rules; POSIX does not copy that operation model.

### Startup contract and old-helper compatibility

Keep `--update-ready <path>` exactly for legacy helpers, writing the actual
installed version as plain text. Introduce a distinct internal argument
`--update-ready-v2 <challenge-path>` so new helper intent is never guessed from
arbitrary existing files. Both go through `cli.main`, not a new desktop entry.

V2 challenge binds transaction ID, random 256-bit nonce, expected BuildIdentity,
manifest digest and canonical install path. Candidate checks private challenge
ownership/location, its **own embedded build stamp**, actual version and install
path; it cannot just echo an expected version read from the challenge. At the
existing shell event-loop milestone it writes a bounded acknowledgement with
that nonce, its identity and the manifest digest, through temp-file + flush +
atomic replace + parent durability. Define a canonical fixed UTF-8 line format
(`HANLY-READY-2`, transaction, nonce, product, OS, arch, version, build UUID,
manifest SHA-256; each on its own line) so the POSIX helper compares exact bytes
without a JSON parser. Strict field rules forbid embedded newlines.

The manifest digest is the verified candidate's transaction identity; the
candidate's build stamp plus prelaunch tree verification establishes what ran.
Do not claim that the ack independently rehashes every dependency. Helpers
remove stale ack before launch and require the live matching transaction;
version-only, wrong UUID/nonce/digest, stale or absent ack never commits. Keep
120-second exit and 600-second startup bounds initially. On timeout or failed
launch, stop **all** target processes before restoring. Persist receipt and
result durably before removing backup; receipt failure leaves recovery material.
Restore prior receipt on rollback; an old version that never had one remains
without one. Do not wait for KRDICT acquisition or OCR warmup to acknowledge.

## 8. Trust, integrity and resource independence

`SHA256SUMS` remains required for supported legacy clients and useful for manual
download verification. It also lists the HUP hash, allowing the new parser to
verify downloaded metadata bytes before opening the ZIP. HUP is the only
application *index* for new clients; sums is a compatibility/integrity sidecar,
not a second application manifest. Hash its bytes through GitHub API asset digest
when supplied; otherwise its authenticity remains the HTTPS release origin.

There is no self-authentication chain: GitHub repository/release access and
HTTPS are the root of trust. A compromised publishing account can replace HUP,
checksums and payloads. HUP hashes defend corruption/mismatched builds, not that
attack. Ad-hoc codesign verifies bundle structure/content, not Thiago's identity.
Do not label checksum validation “publisher signature verified.”

A dedicated HUP signing key would separate release-upload compromise from index
authorization only if key custody and release approval are separate. It adds
key provisioning, offline/public-key embedding, rotation/revocation and recovery;
a secret in the same fully compromised workflow does not establish that separation.
Recommend **defer** for MVP. Revisit with Developer ID/notarization or a concrete
protected/offline release-signing process; no empty signature fields or toy keys.
Refuse downgrades by version normally and use exact identities for same-version
rebuild diagnostics; no automatic same-version replacement in this wave.

Application asset fetches stay bound to the same repository/release, over HTTPS
including redirects to GitHub's delivery hosts. Do not forward credentials to
arbitrary redirect targets. Validate release JSON size/asset count (1 MiB/256
assets), sums size (1 MiB), metadata and archive byte/entry bounds. A corrupt or
unsupported HUP causes an actionable failure; never silently drop to legacy
metadata/full. An unusable optional base or delta yields a separately presented
full choice. Integrity errors never bypass verification, even with confirmation.

**KRDICT stays out of HUP.** Keep `hanly-resources.json` and exactly one versioned
KRDICT `.zst` in the same release. Keep existing carry-forward at draft staging
and independent operator replacement before protected finalization. The resource
manifest's version/hash/schema compatibility governs resources, not app version.
Resource install/rollback and application rollback do not advance/rewind each
other's identities. A resource failure cannot invalidate app startup ack.

Preserve `ResourceFetcher`/`RemoteManifest` and the runtime `updates` configuration
as the later channel boundary. Separate app release snapshots now so future
resource hosting can move without changing HUP. No new endpoint, resource-only
latest release, external repository or resource publication workflow in this wave.
When KRDICT changes without an app code change, the current MVP operational lane
can publish an ordinary app patch release carrying the new pair; clients install
the resource independently. Do not repurpose/mutate published app releases to
make resource-only tags appear latest. A dedicated resource-only publication lane
is deferred; this is a release-cadence limitation, not coupled resource identity.
