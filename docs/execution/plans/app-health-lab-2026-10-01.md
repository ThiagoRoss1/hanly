## Objective and authorized sequence

Build a developer-only **whole-app health lab**, not another OCR benchmark. It must make Hanly's startup, processes, Control Center interactions, capture/hover/popup, settings/resources, updater, shutdown and packaged behavior observable and testable. Its scenarios distinguish verified success, verified failure and not run/unavailable; a green unit test is not a substitute for a real packaged-app check. Use the existing app and test seams, keeping lab code outside shipped packages unless a narrow production correction is evidenced.

1. **Mac foundation (first implementation boundary):** establish the scenario/result contract, safe runner, coverage inventory, privacy rules and a small representative macOS run. Investigate the reported transient second app at launch by identifying its actual process and window identity. Reproduce and correct the update-stage animation only after confirming the UI behavior. Add updater-stage observability and isolated Mac tests as a control, without disturbing the working macOS updater. Stop at the Mac Review Handoff; do not begin the Windows phase on a Mac or Phase B review.
2. **Windows phase (run on the Windows machine after the user resumes it):** add and validate real Windows packaged scenarios. Reproduce the reported install-update loop, determine its first failing stage, fix that cause, and verify installation, relaunch, new-build acknowledgement and owned temporary-directory cleanup. Run the broader Windows coverage matrix and record unavailable conditions honestly. Do not claim Windows acceptance from doubles or Mac results.
3. **Final review (separately authorized):** Claude reads the implementation, checkpoints, evidence and handoff, then investigates correctness, safety, maintainability and unnecessary complexity. Refactoring or extra fixes require the user's authorization and proportional regression checks. This prompt does not authorize automatic Phase B review, push, merge, tag or release.

## Lab design and boundaries

- Place developer-only orchestration under `benchmarks/dev/`, preferably a cohesive `app_lab/` subpackage exposed through the existing `python -m benchmarks.dev` CLI. Put deterministic contract tests with the existing developer tests, native platform checks under `tests/native/`, and frozen-app checks under `tests/packaged/`. Reuse `RunStore`, packaged smoke checks and existing update test fixtures where they fit; do not copy whole implementations into the lab.
- A scenario has a stable ID, platform and prerequisite declaration, safety classification, ordered user/system actions, expected observable transitions, bounded timeout, cleanup ownership, and an outcome of `passed`, `failed`, `not_run` or `unavailable` with a reason. Label observations as real, simulated or inferred. Never turn missing evidence into a success or a zero measurement.
- The initial coverage inventory includes startup/readiness and process roles; Control Center navigation, buttons and state; capture/manual/hover/direct-text/OCR fallback and popup; settings and resource readiness; updater check, plan/confirmation, download, verification, staging, handoff, apply, relaunch, acknowledgement, rollback/cancel and cleanup; quit/reopen; and packaged build identity. Implement a representative vertical slice first, then expand based on coverage gaps and risk. Do not build a large dashboard or generic plugin framework just to display results.
- Normal telemetry records safe stage IDs, timestamps/durations, state transitions, outcome and failure **type**, process role/exit and build identity. It must not persist screen pixels, recognized text, arbitrary exception messages, tokens, credentials, absolute user paths or raw child output. Private captures remain memory-only until an explicit Export into the gitignored `artifacts/benchmarks/runs/` root. Keep production EasyOCR output distinct from staged replay evidence.
- The lab may exercise the actual desktop and packaged binaries, but updater scenarios must use an **isolated test installation and profile**, never the user's everyday app, settings, KRDICT database or install tree. Establish ownership of every test-created directory before deleting it. A real-profile or live-install update requires separate explicit approval. Do not run unattended destructive or privileged system operations.
- Use controlled, versioned test artifacts and an isolated update source for application-update scenarios where possible; do not create, replace or delete a public release to make a test pass. If the current updater has no safe way to point an isolated installation at such a source, document that limitation and obtain a narrow design decision before adding a production configuration surface.
- Preserve `hanly-app → hanly`, the single entry point, three-process boundaries, UI-thread safety and final lookup request-currency check. Do not widen public engine contracts merely for lab evidence. Prefer existing state snapshots, process observation and narrow observation seams. Document any unavoidable production contract change before making it. Keep the app functional when the lab is absent.

## Reported cases and evidence gates

These are reports to investigate, not pre-confirmed root causes or permission for speculative changes.

| Case | Observed report | Required proof and exit condition |
|---|---|---|
| `WIN-UPD-01` | Windows “Install update” downloads, then returns to “Update available” and offers installation again. | On an isolated, real packaged Windows installation, capture current/target build identities and the first failed transition from plan through helper and acknowledgement. After a causal fix, the same update must reach the target build once and not re-offer it. Test failure/rollback separately. |
| `WIN-UPD-02` | An empty `hanly-update` directory remains after the failed attempt. | Record its exact private path and owner, distinguish the install transaction tree from a temporary helper directory, and establish when it was created. Verify cleanup of **owned** remnants after success, cancellation and failure; do not delete an arbitrary similarly named folder or treat cleanup as the cause of `WIN-UPD-01` without evidence. |
| `UI-UPD-03` | “Checking installed files” animates too quickly and appears to restart continuously. | Observe the actual rendered behavior. The update panel currently rebuilds on state render, polling can occur every 500 ms, and the stage-text CSS includes an infinite shimmer; test which animation the user sees. Make the stage-label transition animate once only when the displayed stage text changes, remain stable across progress-only updates, and respect reduced motion. Keep any separate progress indication legible. |
| `MAC-START-04` | Opening Hanly briefly opens another apparent app that closes automatically; the Mac updater works. | Record the process ID/role, bundle/application identity, window/Dock behavior and launch/exit sequence. Determine whether this is an intended child shown incorrectly or a failure before changing lifecycle code. Re-run source and packaged startup after any correction. |

The Windows phase must also probe Control Center actions, capture/hover/popup, startup, quit/reopen and updater under the native packaged build. Do not narrowly declare the lab complete because these four reports are addressed.

## Validation and stop boundaries

For each vertical slice, run focused deterministic tests and the relevant native/packaged scenario. At Mac convergence, run the repository's portable, native, Ruff and mypy gates with the documented interpreter, then a fresh packaged Mac smoke if build-affecting code changed. Record counts and environment-specific skips. On Windows, repeat the Windows native and packaged gates plus a real isolated update; compare against the Mac control. Do not weaken a gate to make a scenario green. If an environment blocks a native check, record `unavailable` and the precise reason.

Keep reproducible technical evidence, not routine progress prose, in `docs/execution/reports/app-health-lab-2026-10-01.md` if the investigation warrants it. Store private run output only under the gitignored artifact root and never commit it. At the end of each authorized implementation boundary, update the checkpoint and write a concise Review Handoff under `docs/execution/review-handoffs/` using its template. Stop there. A later reviewer must be human-selected and separately authorized.

Keep changes logically separated; combine tiny related fixes rather than making noisy one-line commits. Write every subject and body in English. Use the repository's conventional subject form (`feat:`, `fix:`, `chore:` or `docs:`), followed by a concise imperative summary; use short `- Adds …`, `- Fixes …` or equivalent action bullets in the body. Use the configured human author only, with no assistant/co-author attribution. Do not amend, squash, rebase or rewrite earlier commits without explicit instruction. The user will perform the push and merge; this prompt does **not** authorize either, nor a tag or release.
