## 2. Executive summary and priority calls

The strongest V1 concerns currently supported are (1) a reproducible stale direct-lookup result after pointer movement, (2) the unresolved product decision about the Control Center OCR selector, (3) an explicit private Export that can be directed outside the stated gitignored artifact root, and (4) a smoke-database command that can overwrite an existing database at the caller-supplied destination. The leading-whitespace cursor defect is confirmed in the public engine API but has no identified shipped desktop caller (A-02, P3). The updater's empty-directory deletion shape and transient readiness-waiter growth are also reproduced. The two Vision test failures are restricted-environment observations, not demonstrated product defects.

Other evidence points to a stale live first-release runbook, an ignored schema-version contract, inaccurate derived documentation, accessibility gaps, and redundant helpers/exports. Q6 also verified a crash-leftover scratch cleanup gap and a narrow multi-volume DMG detach-reporting gap. Candidate code cleanup should wait for the reviewer to verify public API and packaging consequences. No broader Vision-quality or platform-acquisition failure was established by this audit.

**V1 first:** resolve A-01 and the A-03 product decision; verify the scope and correction of N-06 (Export destination) and N-08 (smoke-database overwrite); reconcile the live-looking release runbook with the current asset contract. Then assess A-05, A-02, A-24, and the limited updater-recovery findings. Keep A-04 as a restricted-test-environment limitation, not a product regression. The final reviewer must validate priorities and propose one approved implementation scope.

**Later or conditional:** broad module moves, helper cleanup, accessibility policy changes, copy refinement, and concurrent-controller ordering unless the reviewer establishes them as active V1 requirements. Benchmark fidelity matters before using stage-specific measurements for a product decision; N-01/N-03 do not themselves overturn the measured Vision-versus-EasyOCR outcome. No broader redesign or architecture change is approved here.

### V1 correctness, product policy, and operations

**A-01 — Direct lookup can present after pointer movement.** Category: concurrency/stale results. Status: **Verified** for movement; pause portion narrowed. Severity P2; confidence high; independently reproduced by Q2 and Q3. Files: `packages/hanly-app/src/hanly_app/hover_lookup.py:326-335,365-373,484-494,801-815,858-874,926-954`; coverage: C2, Q2, Q3. The OCR submission path records its active lookup request ID; `_submit_direct_text` does not. `_on_position` invalidates only the stored ID before scheduling the next hover request. Both Q2 and Q3 used a blocked worker and observed the old direct request remain current/uncancelled and its result delivered after a second pointer position. Q2 also invoked the runtime’s `pause()` directly and saw delivery; Q3 traced normal production stop/mute callers and found they invalidate the shared controller before calling `pause()`. Thus the normal pause route is not shown defective; the direct runtime-only pause sequence is a narrower internal edge. Impact: a result for the previous pointer target can appear during the next dwell/acquisition interval. Direction: register direct submissions in active-request bookkeeping and retain a post-submit currency check; add a movement barrier test, and only add a pause test at the production entry point if it can reach the runtime without prior invalidation. Risk: changes affect popup timing/order. Platforms: all app paths using direct selection. Validate: deterministic race test plus focused hover/direct tests. **Sonnet pass: CONFIRMED by the coordinator.** A fresh barrier repro drove the real `HoverLookupRuntime` and `LookupController` with a blocked worker and called `_invalidate_active_hover()` (the call `_on_position` makes at `hover_lookup.py:487`). With the capture route (`_capture_and_submit`) the result was delivered **0** times; with the direct route (`_on_direct_text` → `_submit_direct_text`) it was delivered **1** time. The asymmetry is that only the capture route sets `_active_hover_request_id` (`hover_lookup.py:801-815`). Caveat: a later hover submission is latest-wins and supersedes the old request, so the stale popup can appear only inside the movement-to-next-submission window.
